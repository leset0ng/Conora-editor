# Conora CLI

A non-interactive, local CLI for creating CRPack v1 resource packs. A theme supplies reusable icon source images; each firmware target supplies real resource paths and its own original encoding templates. No AI provider, AstroBox host or device connection is required.

## Installation

From this repository:

```bash
cargo install --path crates/conora-cli --locked
conora --help
```

After `conora-core` and `conora-cli` are published to crates.io:

```bash
cargo install conora-cli --locked
```

The installed executable is `conora`, not `conora-cli`. These crates are prepared for publication but are not published by this change. Rust 1.88 or newer is required. The existing AstroBox plugin remains a separate WASM build.

## One theme, multiple firmwares

```text
my-icons/
├── theme.json
├── assets/
│   ├── confirm.png
│   └── confirm-wide.png
├── previews/
└── targets/
    ├── band11-A.json
    └── band11-B.json
```

Initialize a theme and pin two firmware inputs:

```bash
conora init my-icons --theme-id dark --name "Dark Icons" \
  --firmware /path/to/firmware-A.bin --target band11-A \
  --device xiaomi-band-11-4.100.155
conora target add band11-B --theme my-icons \
  --firmware /path/to/firmware-B.bin --device another-firmware
```

`init` creates empty role/binding maps: it does not guess which resources represent an icon. It also works without `--firmware`; add targets later. `target add` records the SHA-256 of the entire firmware and refuses to overwrite an existing target unless `--force` is given. Replacing a target resets its bindings/overrides; review the new firmware and re-add them deliberately.

Inspect each firmware and extract original reference images:

```bash
conora ls --theme my-icons --target band11-A --images --json
conora ls --theme my-icons --target band11-B --images --search confirm --json
conora extract --theme my-icons --target band11-A \
  --resource app/common/icon/confirm.bin --as png \
  --output my-icons/previews/confirm.png
```

You can inspect/extract a firmware without a theme using `--firmware /path/to/firmware.bin` instead of `--theme ... --target ...`. `ls` returns recognized image dimensions, stride and format along with exact resource paths. Search is a case-sensitive substring match. Unsupported resources remain extractable with `--as raw` (the default).

Declare shared source assets in `theme.json`:

```json
{
  "schemaVersion": 1,
  "themeId": "dark",
  "name": "Dark Icons",
  "version": "1.0.0",
  "author": "Example author",
  "icons": {
    "confirm": "assets/confirm.png"
  }
}
```

`version`, `author` and `description` are optional. `themeId` is 1-12 lowercase ASCII letters, digits, `_` or `-`. Icon roles are nonempty strings of up to 128 UTF-8 bytes without control characters. Source files are resolved **relative to the theme file**, not the shell working directory. No assets, previews or other files are packaged unless a declared role has an explicit target binding.

Edit each generated `targets/<id>.json`, preserving its actual `firmwareSha256`:

```json
{
  "schemaVersion": 1,
  "firmware": "../../firmware-A.bin",
  "firmwareSha256": "<the 64-character hash generated by target add>",
  "device": "xiaomi-band-11-4.100.155",
  "bindings": {
    "confirm": "app/common/icon/confirm.bin"
  }
}
```

The placeholder above is documentation, not a usable hash. Firmware paths are resolved **relative to the target config**. Generated paths are relative where possible; keep the firmware in a portable location if moving the project. Only the complete firmware is fingerprinted: individual resources and source assets have no stored hashes.

A role can bind multiple copies in a firmware:

```json
{
  "bindings": {
    "confirm": [
      "app/common/icon/confirm.bin",
      "app/another/icon/confirm.bin"
    ]
  }
}
```

These snippets show fields to edit in the existing target config, not complete standalone configs. Every theme role needs a nonempty binding in each selected target. Unknown roles, repeated resource paths and nonexistent firmware resources are errors. Target IDs are 1-64 ASCII letters, digits, `_` or `-`. Config schema versions other than 1 and unknown config fields are rejected.

### Target-specific source overrides

Different firmware dimensions can require different artwork. Add an override to that target:

```json
{
  "overrides": {
    "confirm": "assets/confirm-wide.png"
  }
}
```

Override paths are also relative to the **theme file**, not `targets/`. They replace that role's source/options only for the target. An override must refer to an existing, bound theme role.

### Explicit conversion options

A string asset is shorthand for PNG conversion without palette quantization. A detailed asset can be used in `icons` or `overrides`:

```json
{
  "confirm": {
    "input": "assets/confirm.png",
    "mode": "png",
    "allowQuantize": true
  }
}
```

`mode` defaults to `png`; `allowQuantize` defaults to `false`. Conversion uses each bound resource's original template, preserving dimensions/stride/layout. Matching aspect ratios are resized with nearest-neighbor sampling; different ratios are rejected, never cropped, stretched or padded. Palette reduction beyond the target palette capacity requires explicit opt-in. RGB565/alpha-only formats and JPEG can intrinsically lose precision/transparency even without palette quantization; conversion reports indicate loss where detected.

For arbitrary binary replacement, use `{"input": "assets/file.bin", "mode": "raw"}`. Bytes are copied unchanged; diagnostics warn that the device-specific format is not certified.

## Check and build

```bash
conora check --theme my-icons --target band11-A --json
conora check --theme my-icons --all-targets --json
conora build --theme my-icons --all-targets
conora build --theme my-icons --target band11-A --output ./packs --force
conora inspect ./packs/dark-band11-A.crpack --json
```

- Choose exactly one of `--target ID` or `--all-targets`.
- `--theme` accepts a directory or a theme JSON file, and defaults to `.` for target management/check/build.
- `check` performs conversion and pack validation, but writes no outputs.
- `build --output` is always a **directory**. Explicit output paths are relative to the shell working directory; the default is `dist/` inside the theme project.
- Filenames are `<themeId>-<target>.crpack`.
- All selected targets must validate and outputs must pass preflight before any pack is published. Targets are prepared one at a time, with temporary files staged in the output directory rather than retaining all pack bytes in memory; then each pack is atomically committed. If a filesystem failure occurs during commits, the error reports already published paths and `partialCommit`; multiple-file commits are not a transaction.
- Existing output files require `--force`. It does not authorize overwriting source firmware, theme/target configs or known source assets, including aliases.
- `extract` follows the same no-overwrite/atomic-file-write rules. When given a theme, it protects project inputs; direct `--firmware` extraction protects its firmware input.
- `inspect` strictly validates the archive and reports its original manifest, ordered mappings, targets and file sizes; it does not need a firmware or rewrite the pack.

CRPack v1 has no target-dependent resource branches. These builds intentionally create separate packs; they do not infer or automatically merge cross-firmware compatibility. Optional `device` becomes advisory manifest `targets[0]`, not a compatibility guarantee.

## Machine-readable output

`--json` is a global option and can appear before or after a command. It writes one JSON result to stdout with `schemaVersion: 1`, `ok` and `command`. Any human diagnostics use stderr. Help/version remain normal text, even with `--json`.

Check/build results contain `targets`, an array of target reports. Successful builds also contain `outputs`. A target report includes `valid`, `firmwareSha256`, successful `resources`, `errors`, `warnings` and `packBytes`. Diagnostics include a stable `code` and a human-readable `message`, plus `role`, `resource` and `input` when applicable. Useful diagnostic codes include `missing_binding`, `missing_resource`, `duplicate_binding`, `asset_input`, `unsupported_template`, `template_size`, `image_conversion`, `pack_validation`, `raw_unverified` and `lossy_conversion`.

On failure, top-level `errors` describes the command failure. Validation failures retain the per-target reports so an agent can fix multiple independent issues in one iteration. Successful resources in a failed report do not imply that a pack was emitted.

Exit codes:

| Code | Meaning |
| --- | --- |
| 0 | Success, help or version |
| 1 | Input, validation or filesystem failure |
| 2 | Invalid command-line usage |

## Limits and boundaries

Native CLI firmware inputs are limited to 512 MiB; config files to 1 MiB; source assets, original conversion templates and extracted resources to 64 MiB each. PNG decoding is additionally limited to 16 * 1024 * 1024 pixels. Inputs must be regular files; Unix FIFOs are rejected without blocking. Native CLI paths used in configs/results must be representable in UTF-8.

CRPack output follows v1: one root `canora.json`, safe resource paths, at most 256 mappings, at most 64 KiB manifest, at most 32 KiB generated mapping configuration and at most 64 MiB total uncompressed content including the manifest. The container has no file-count cap; Interconnect transfers still have a 65,536-file index limit, and older Managers can impose further limits. `mappings.tsv` is derived on-device and must not be included in a pack.

The CLI does not modify firmware, install themes, talk to watches, call image generators, or guarantee on-device appearance. A coding agent can produce/edit source PNGs and configs, then run `check` and `build`; use the AstroBox editor or the device to visually review the results.
